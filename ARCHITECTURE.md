## 1. Product summary

Automated SF apartment-matching service. Polls rental listings from multiple sources around the clock, deduplicates across sources, geocodes addresses, matches each subscriber's saved criteria, and texts matching listings to their phone via SMS. One-time access passes ($39/30-day, $69/90-day); no recurring subscription — the product churns by design when users find an apartment. Fast-follow of ApartmentHunter3000.

## 3. Data model (lib/db/schema.ts)

**users** — id (uuid PK), phone (unique), status (enum: pending_payment | active | expired | done), plan (enum: pass_30 | pass_90), access_expires_at, created_at, quiet_start (time, default 21:00:00), quiet_end (time, default 08:00:00), max_daily_sms (int, default 20), notifications_paused (bool, default false). The four notification-preference columns were added in AH-019 (migration `drizzle/0001_ah-019-notification-settings.sql`) — see §4/§7 for how they're enforced.

**listings** — id (uuid PK), source, source_id (unique together), address, lat, lng, price, beds, baths, sqft, url, posted_at, first_seen_at, is_canonical (bool), canonical_id (uuid, points to canonical listing for dedupe), raw (jsonb), pets_allowed (text, nullable, AH-018), laundry_type (text, nullable, AH-018), amenities (jsonb, nullable, AH-023), images (text[], nullable). Indexes: geo (lat,lng), unique(source, source_id). `images` (migration `drizzle/0007_listing-images.sql`) is a flat array of image URL strings, parsed per-source at poll time (see §7 `lib/listingImages.ts`) — `images[0]` is the primary/thumbnail image by convention (parsers order the strongest single image first). Plain `text[]` rather than jsonb, matching the `zips`/`neighborhoods` array-column convention on `criteria` below (the shape is uniform across sources — a flat URL list — unlike `raw`/`amenities`, which need jsonb for their genuinely varying per-source/per-computation shape). Every parser returns `[]` rather than null when a listing has no images (never a guess); the column stays nullable only so pre-existing/test callers that omit the field entirely don't need updating. `pets_allowed`/`laundry_type` are plain `text`, not a Drizzle `pgEnum` — the value domain is parser-derived (see §7 `lib/listingAttributes.ts`) and null always means "couldn't parse this from the source data," never a guess at "no pets"/"no laundry". Domain: `pets_allowed` ∈ {`cats`, `dogs`, `cats_and_dogs`, `yes`, `no`, null}; `laundry_type` ∈ {`in_unit`, `hookups`, `on_site`, null}. `amenities` (AH-023) is a **cached** nearby-grocery/gym/transit/bike-share result, untyped jsonb (same convention as `raw`/`criteria.commute_isochrone`) — callers cast via `lib/amenities.ts`'s `ListingAmenitiesCache` type. Null means "not computed yet" (this listing's detail card has never been opened); an empty `amenities: []` array is a real, cacheable "computed successfully, nothing found within 0.5mi" result — the two are deliberately distinct so a genuinely amenity-poor listing doesn't get re-queried against Mapbox on every pageview.

**criteria** — user_id (uuid PK, FK → users ON DELETE CASCADE), price_min, price_max, beds_min, beds_max, baths_min, baths_max (AH-024, migration `drizzle/0008_ah-024-bathrooms-filter.sql`), zips (text[]), neighborhoods (text[]), pets (text, nullable, AH-018), laundry (text, nullable, AH-018), commute_address/commute_max_minutes/commute_mode/commute_isochrone (AH-017, all nullable). **AH-024:** `baths_min`/`baths_max` are `real`, not `integer`, mirroring `listings.baths`'s own type — half-baths (e.g. 1.5) are common in real SF rental data and every poller already populates them that way, so an integer-only criteria column would be unable to express a range match against genuine listing values. `pets` ∈ {`cats`, `dogs`, `cats_and_dogs`, null=no preference}; `laundry` ∈ {`in_unit`, `on_site`, null=no preference} — narrower than `listings.pets_allowed`/`laundry_type` since a subscriber states a need, not an observed value. `commute_mode` ∈ {`transit`, `bike`, `drive`, null=no commute filter}; `commute_isochrone` (jsonb, untyped at the schema level like `listings.raw`) is a **cached** polygon + metadata computed once via `lib/commute.ts`'s `computeCommuteIsochrone()` whenever the three commute fields are set/changed — see §4/§7 for the caching design and the transit-mode approximation.

**sent** — user_id + listing_id (unique together, both FK with CASCADE), sent_at. Tracks which listings have been texted to which users to prevent duplicates. read_at, dismissed_at (both nullable timestamps, added AH-016) — null = unread / not dismissed; set to the action time when the user reads or dismisses the item in the in-app inbox. No surrogate id column; rows are addressed by the (user_id, listing_id) pair the unique constraint is already built on.

**favourites** (AH-022) — user_id + listing_id (unique together, both FK with CASCADE) + saved_at. Deliberately the same shape/conventions as `sent` above. No surrogate id column, same reasoning. Re-saving an already-saved listing is idempotent via the unique constraint + `onConflictDoNothing()` on insert (matches `sent`'s own upsert convention in `twilioSender.ts`) rather than a SELECT-then-INSERT race — verified directly against the live DB (two inserts of the same pair produce exactly one row, no error), not just mocked in unit tests.

## 4. Core pipeline (Inngest functions)

All functions in `inngest/functions/`. Registered in `app/api/inngest/route.ts`.

**rentcastPoller.ts** — Cron: every 6h (`0 */6 * * *`), plus a manual `app/rentcast.manual-poll` trigger. Calls RentCast API for SF rental listings (`limit=500`). Budget-capped via `lib/pollerBudget.ts` (`claimDailyBudget`, max 20 req/day, Redis-backed) as an independent safety net on top of the cron schedule itself (see the RentCast cost-bleed incident in the memory checkpoint tree). Upserts into listings table (source='rentcast') via `dedupeAndUpsertListings`, chunked into multiple `step.run()` calls of 50 items each so no single Inngest step invocation exceeds the route's 60s `maxDuration` — up to 500 sequential DB round-trips in one step reliably timed out otherwise (fixed 2026-07-16, issue #40). **AH-018:** maps `pets_allowed`/`laundry_type` via `lib/listingAttributes.ts`'s `parsePetsFromRentcast`/`parseLaundryFromRentcast` — both currently always return null, confirmed empirically against all 801 live rows in production that RentCast's `/v1/listings/rental/long-term` response contains no pet/laundry field anywhere (address/price/beds/baths/sqft/property-type/listing-history/MLS info only); the parsers are real, tested extension points in case RentCast adds this data later, not dead code. **Images:** maps `images` via `lib/listingImages.ts`'s `parseImagesFromRentcast` — always `[]` today, same "confirmed against live data, not assumed" finding as the pets/laundry parsers (checked all keys across 895 live rows plus a fresh live API call, 2026-07-17; this endpoint has zero photo/image data). Emits `app/listings.upserted` for canonical IDs.

**craigslistPoller.ts** — Cron: every 2h (`0 */2 * * *`). Craigslist's own RSS feeds (`?format=rss`) are blocked site-wide as of 2026-07-16 (confirmed independently, not IP/UA-specific) — listings now come from an Apify actor (`memo23/craigslist-scraper`, residential-proxy routed) instead, capped at 80 items/run via `MAX_ITEMS_PER_RUN`. Requires `APIFY_API_TOKEN` in Vercel env vars; fails closed with a clear error if missing. Budget-capped via the same `claimDailyBudget` pattern (max 24 runs/day). Same chunked-upsert fix as rentcastPoller, applied preemptively (not yet triggered at the 80-item cap, but same latent failure mode). **AH-018:** maps `pets_allowed`/`laundry_type` via `lib/listingAttributes.ts`'s `parsePetsFromCraigslist`/`parseLaundryFromCraigslist` — the actor normalizes Craigslist's own housing checkboxes into a structured `amenities` string array (e.g. `"cats are OK - purrr"`, `"w/d in unit"`, `"laundry in bldg"`), confirmed against a live sample run; that structured field is checked first, with a free-text regex fallback over `title`+`post` only for listings where the poster didn't tick the corresponding checkbox. **Images:** maps `images` via `lib/listingImages.ts`'s `parseImagesFromCraigslist` — the actor's `pics` field is a flat array of ready-to-use direct image URL strings (e.g. `images.craigslist.org/...`), confirmed against a live 3-item actor call (2026-07-17); the simplest of the three sources' image shapes, no normalization beyond filtering to non-empty strings. Emits `app/listings.upserted`.

**facebookPoller.ts** (AH-014) — Cron: every 2h, offset 15min from craigslistPoller (`15 */2 * * *`), so the two Apify-backed pollers don't contend for DB connections at the same minute. Listings come from an Apify actor (`memo23/facebook-marketplace-scraper-ppe`), chosen over the official `apify/facebook-marketplace-scraper` after live-testing both: the official actor (8.5k users, but only 3.45/5 rating and no documented proxy/compliance approach) returned listings from Rocky Mount, NC for an SF-scoped query — it doesn't reliably honor geographic targeting. `memo23`'s actor explicitly documents built-in residential-proxy routing (same standard as the Craigslist swap) and correctly returned real SF Bay Area listings on every live test. Run with `includeSeller: true` and `daysSinceListed: '1'` — the former returns real per-listing GPS + timestamps at no extra line-item cost (folded into the flat $0.0015/result price), skipping the geocoding fallback for the common case same as craigslistPoller; the latter limits each run to listings from the last day so repeat runs don't re-bill for the same still-live items. Beds/baths aren't structured fields on this actor — parsed via regex from the listing title text (`"3 beds · 2 baths"`), null when absent (e.g. non-apartment "propertyrentals" listings). No square footage available from this source. Capped at 80 items/run, budget-capped via `claimDailyBudget` (max 24 runs/day) — same pattern and caps as craigslistPoller; worst case ~$1.50/day (~$45/month) at the actor's $0.0015/result + $0.005/run pricing. Requires `APIFY_API_TOKEN` (shared with craigslistPoller); fails closed with a clear error if missing. Same chunked-upsert pattern as the other two pollers. **AH-018:** does not map `pets_allowed`/`laundry_type` — this poller landed the same day as AH-018 in a separate parallel worktree, so `facebookPoller.ts`'s upsert mapping predates `lib/listingAttributes.ts` and currently omits both fields (they default to null via `lib/listings.ts`'s optional `petsAllowed?`/`laundryType?`, so nothing breaks — matches are simply never filtered on Facebook Marketplace pet/laundry data yet). Worth a small follow-up to wire in `parsePetsFromCraigslist`/`parseLaundryFromCraigslist`-style parsing once this actor's own field shape (amenities/description text) is inspected. **Images:** maps `images` via `lib/listingImages.ts`'s `parseImagesFromFacebook` — confirmed via a live 3-item actor call with `includeSeller: true` (2026-07-17) that the actor exposes two image fields: `moreDetails.listing_photos[].image.uri` (the full gallery — one live listing had 14 photos) and `primary_listing_photo.photo_image_url` (a single cover photo, always present). The gallery is preferred when present (it already includes the primary photo as its first element, confirmed by matching photo IDs); `primary_listing_photo` is only a fallback for the case where `moreDetails` is absent. Facebook's CDN URLs are signed/expiring (`oe=` query param) — unlike Craigslist/RentCast, these will eventually 404; accepted tradeoff of linking Facebook's own CDN rather than re-hosting images, same "link out, don't proxy" approach this codebase already takes for `url`. Emits `app/listings.upserted`.

**realtorPoller.ts** — Cron: every 2h, offset 30min (`30 */2 * * *`) so it doesn't collide with rentcastPoller/craigslistPoller (minute 0) or facebookPoller (minute 15). Listings come from an Apify actor (`kawsar/realtor-Search`), chosen after live-testing three real candidates against real SF `status=for_rent` searches: `memo23` (this project's preferred publisher for Craigslist/Facebook) has **no** Realtor.com rental actor at all — their only Realtor.com actor is agent-lead-gen/for-sale focused with no rental search mode, confirmed via its input schema before ruling it out; `solidcode/realtorcom-scraper` (cheapest candidate) failed outright on a live call (`"Collecting session cookies"`, an anti-bot wall); `automation-lab/realtor-scraper` succeeded live but only exposes a single cover photo per listing, no gallery. `kawsar/realtor-Search` succeeded on every live test (3 runs, 100% success), is the cheapest working candidate ($0.00167/result), and is the only one exposing a real photo gallery (`photo_urls`). **Live-tested finding worth knowing before touching this further:** Realtor.com's own `status=for_rent` SF results are real but noisy — a live 20-item sample found only 4/20 (20%) genuine listings with real price/beds/baths (`source_type` `mls` or `unit_rental`); the other 16/20 (80%) are `source_type: "community"` Zillow/Appfolio syndicated placeholder rows with `list_price: null` and no usable data at all. `upsertApifyRealtorListings` filters these out (drops any item without a real `list_price`) before ever mapping/upserting them — same "drop rather than guess" convention as every other parser in this codebase, since a null-price listing is unmatchable and useless in an SMS. This means Realtor.com's genuine usable rental inventory for this product is real but meaningfully thinner than Craigslist/Facebook Marketplace, as the ticket that spawned this poller anticipated. Scope is also narrower than the other two Apify pollers: this actor's input only searches one city per call (no sfbay-wide subdomain, no lat/lng+radius), so this poller covers San Francisco proper only, not the wider Bay Area — a reasonable future follow-up if this source proves valuable enough to extend. Capped at 35 items/run, budget-capped via `claimDailyBudget('realtor-poller', 24)` (2x the 12 scheduled runs/day, same headroom convention as the other two Apify pollers) — worst case ~$1.40/day (~$42/month), under this project's ~$1.50/day-per-poller ceiling; normal-case cost (no retries) is about half that. Requires `APIFY_API_TOKEN` (shared with craigslistPoller/facebookPoller); fails closed with a clear error if missing. Same chunked-upsert pattern as the other pollers. **Images:** maps `images` via `lib/listingImages.ts`'s `parseImagesFromRealtor` — this actor's `photo_urls` field is already a flat array of ready-to-use rdcpix.com CDN URLs (the full gallery, one live listing had 49 photos), simpler than Facebook's nested gallery shape; falls back to `primary_photo_url` when the gallery is empty/absent. Does not map `pets_allowed`/`laundry_type` — this actor's dataset schema has no description/amenities field to parse them from (confirmed via its full field list during live testing), same gap as facebookPoller.ts. Emits `app/listings.upserted`.

**apartmentsPoller.ts** (2026-07-17, not an AH-XXX ticket — one of 5 new listing sources Pranav asked for directly, see CLAUDE.md) — Cron: every 2h, offset 37min (`37 */2 * * *`), a distinct slot from craigslistPoller (`:00`), facebookPoller (`:15`), and realtorPoller (`:30`). Listings come from an Apify actor (`epctex/apartments-scraper-api`), chosen after live-testing it head-to-head against the next-best candidate (`one-api/apartments-property-scraper`) out of 9 Apartments.com actors surveyed in the Store: epctex has by far the highest usage (319 total/55 monthly users) and the only meaningful review history of any Apartments.com actor (5.0/5 across 11 reviews — every other candidate, including one-api, has zero or near-zero ratings); both were live-tested with a real `search: "San Francisco, CA"` call and both returned correct, real, correctly geo-scoped SF properties (ruling out an actor-quality problem for this category the way the official Facebook Marketplace actor had a real region bug), but only epctex exposes real per-unit numeric beds/baths/price/sqft (via `rentals[]`) in the same single call — one-api's default output is a property-level record with range strings only (`"$3,380 - 9,236"`), which would need a second per-property detail call to get usable per-unit numbers. **Design — one listing row per available unit, not per property:** Apartments.com lists professionally-managed communities, each with several floor plans and, within each floor plan, several individually-priced currently-available units; a single property-level row with range-string price/beds/baths wouldn't work with `matchingEngine.ts`'s numeric range filters (a $2,500-3,500 search would trivially "match" a property whose range is $3,900-9,500 with no actual unit in range). `apartmentsPoller.ts` flattens each fetched property's `rentals[]` (the actor's real list of currently-available, individually-priced units — not `models[]`, which is the property's full historical floor-plan catalog including plans with zero available units) into one listing row per unit via `flattenApartmentsUnits()`, `sourceId` = `` `${propertyId}-${rentalKey}` ``, so `matchingEngine.ts`'s existing numeric filters apply unchanged. **A real mistake caught during live-testing, not guessed around:** `postedAt` is derived from the property-level `lastUpdated` relative-time string (`"2 hours ago"`, parsed by `parseRelativeUpdatedAt()`), never from `rental.availableDate` — the latter is a future move-in date (one live NEMA unit had `availableDate` two months out against a same-day `lastUpdated`), and passing a future date into `lib/format.ts`'s `timeAgo()` would silently render as "just now" (negative-hours falls into its `hrs < 1` branch) rather than crashing, which would have been a materially wrong freshness signal on the dashboard map's recency-colored markers had it shipped unnoticed. Capped at 30 properties/run (`MAX_PROPERTIES_PER_RUN`, not a row cap — each property fans out into ~15 unit rows on average, observed 10/32/13/15/5 across the 5 live-tested properties), budget-capped via `claimDailyBudget` (max 24 runs/day, same 2x-headroom convention as the other two Apify pollers). Cost math (epctex's actual PAY_PER_EVENT pricing: $0.01/list-page-query incl. first 20 items free + $0.0005/item beyond that, no optional add-ons enabled): roughly $0.025/run, ~$0.30/day at the 12-runs/day scheduled cadence, comfortably under this project's ~$1.50/day-per-poller convention — see the poller's own header comment for the full math and why it's also cheaper than one-api's flat per-result pricing would have been at this item count. Requires `APIFY_API_TOKEN` (shared with the other two Apify pollers). Same chunked-upsert pattern (50/chunk). Does not map `pets_allowed`/`laundry_type` (same scoped-out-for-now state as facebookPoller.ts — a reasonable follow-up once the property `amenities`/fee-policy text is inspected for pet-policy signal). **Images:** maps `images` via `lib/listingImages.ts`'s `parseImagesFromApartments` — each `rentals[]` unit carries its own real per-unit floor-plan photo URL (`images1.apartments.com` CDN) in the free default response (the actor's paid `includeVisuals` option, not enabled, would add a fuller interior/exterior gallery); confirmed live that `image` is absent on some units within a real property response, so this degrades to `[]` rather than guessing. Emits `app/listings.upserted`. **Verified end-to-end against real data, not just mocked tests:** ran the real `flattenApartmentsUnits()`/`upsertApifyApartmentsListings()` functions (imported directly, via a disposable local script deleted before commit) against a real 3-property/55-unit dataset captured live via the Apify actor during this session's research, writing 4 real rows through the actual `dedupeAndUpsertListings()` code path into the live production DB, confirming via direct `execute_sql` read that address/price/beds/baths/sqft/lat/lng/images/postedAt/isCanonical all landed correctly (e.g. real floor-plan photo URLs, `postedAt` correctly resolved to ~2 hours before the write, not the far-future `availableDate`), then deleting those 4 rows and re-confirming zero `source='apartments'` rows remained — unlike the "Listing images" session's precedent of leaving seeded real data in place, this poller's rows were cleaned up since the source hadn't merged/shipped yet at verification time.

**spareroomPoller.ts** — Cron: every 2h, offset 50min from craigslistPoller (`:00`) (`50 */2 * * *`), distinct from facebookPoller (`:15`), realtorPoller (`:30`), and apartmentsPoller (`:37`) so every Apify-backed poller on this cadence fires in its own minute and none contend for the same DB connections. **Originally shipped at `:30`, which collided with realtorPoller.ts's own `:30` once both merged into `main` the same day** — moved to `:50` during that merge (the exact "sanity check once all 5 have merged" apartmentsPoller.ts's own header comment anticipated). Room-share/roommate-matching source — intentional addition alongside 4 sibling sources (Apartments.com, Zumper, Apartment List, Realtor.com) requested directly by Pranav on 2026-07-17 (not from the AH-XXX backlog — see `CLAUDE.md`), each built as a parallel background agent. Listings come from an Apify actor (`memo23/spareroom-scraper`), the same publisher as `craigslistPoller.ts`/`facebookPoller.ts`, chosen for the same proxy-routing standard — its input schema explicitly documents a built-in residential proxy, unlike most of the ~7 other SpareRoom actors on the Apify Store, which either don't mention proxy handling at all or are UK-only. **Live-testing found the same class of bug the AH-014 Facebook actor evaluation hit** — advertised geo-targeting that silently doesn't work: a call with the actor's documented "bare US city name" input mode (`startUrls: ["San Francisco"], country: "US"`) returned 5 real (not fabricated) listings from Phoenix AZ, rural Louisiana, Flushing NY, Jersey City NJ, and San Bernardino CA — zero from the Bay Area. Root-caused by reproducing the search on spareroom.com directly: a bare location string only resolves correctly through the site's autocomplete (which attaches an internal location ID), not as a plain query param. Fix: `SF_SEARCH_URL` is a fixed, pre-resolved `https://www.spareroom.com/roommate/?search_id=...` URL (captured once via a real browser search + autocomplete selection), passed as `startUrls` instead of a bare city name. A second live call with that URL correctly returned 5/5 genuine SF listings (Russian Hill, Nob Hill, SOMA/South Of Market, real lat/lng in SF, real photos) — confirmed via `get-dataset-items`, not just the actor's run summary; also confirmed the URL resolves from a cookie-less `curl` (not tied to the browser session that generated it) and SpareRoom's own UI treats these as stable, shareable links ("Save search for alerts" is a site feature on the same URL). **Beds/baths judgment call** (per the ticket — SpareRoom's ad model is one room within a shared property, not a whole unit, unlike every other source): `beds` is `1` for the common single-room-ad case (`available_as_whole_property !== 'Y'`) — the one room being rented, not `rooms_in_property` (the shared property's *total* bedroom count, which would overstate what a subscriber actually gets); whole-property ads (`available_as_whole_property === 'Y'`) use `rooms_in_property` instead, matching every other source's "bedrooms in the unit offered" semantics. `baths` is `1` when `rooms[0].ensuite === 'Y'` (this room has a private bathroom — a real, useful signal) and `null` otherwise (shared/unknown, not a guessed total — the actor exposes no property-wide bathroom count at all). `sqft` is always `null` — confirmed absent across the actor's full ~200-field output on two live test runs. `postedAt` is derived from `basicInfo.daysOld` (day-granularity only — no timestamp field exists on this actor), same "documented approximation" honesty standard as AH-017's transit multiplier. Capped at 40 items/run (`MAX_ITEMS_PER_RUN`) — SF's entire active SpareRoom inventory was ~65 listings at live-test time, a much smaller/slower-churning pool than Craigslist/Facebook's rental volume, so 80 would mostly re-scrape the same static listings. Budget-capped via `claimDailyBudget('spareroom-poller', 24)` — same 2x-scheduled-runs headroom pattern as the other Apify pollers; cost ceiling ~$1.03/day (~$31/month) worst case at the actor's $0.00095/result + $0.005/start pricing, comfortably under this project's ~$1.50/day-per-poller convention. Requires `APIFY_API_TOKEN` (shared with craigslistPoller/facebookPoller); fails closed with a clear error if missing. Same chunked-upsert pattern as the other pollers. Does not map `pets_allowed`/`laundry_type` (out of this ticket's scope, same documented-follow-up precedent as `facebookPoller.ts`). **Images:** maps `images` via `lib/listingImages.ts`'s `parseImagesFromSpareRoom` — the actor's `photos[]` array of objects, each with several pre-sized URL variants; `large_url` is used per photo, confirmed against a live 5-item actor call (2026-07-17, 2-18 photos per listing). Emits `app/listings.upserted`.

**apartmentListPoller.ts** — Cron: every 6h (`30 */6 * * *`, offset 30min from rentcastPoller's `0 */6 * * *` so the two 6h-cadence pollers don't contend for DB connections). **matchingEngine.ts** — Triggered by `listing/new` event. Geocodes via Mapbox if lat/lng missing. Runs cross-source dedupe (sets is_canonical/canonical_id). For canonical listings: queries all active, non-paused users whose criteria match (price range, beds range, **AH-024: baths range**, neighborhood/zip overlap, **AH-018: pets/laundry compatibility**, **AH-017: commute-time compatibility**), excluding already-sent pairs. **AH-024:** `findMatchingUsers()`'s SQL gained a baths range clause, `(baths::real IS NULL OR c.baths_min IS NULL OR c.baths_min <= baths::real) AND (baths::real IS NULL OR c.baths_max IS NULL OR c.baths_max >= baths::real)` — the exact same null-passthrough pattern as the beds range clause immediately above it, added immediately after it. **AH-018:** `findMatchingUsers()`'s SQL gained two more optional-filter clauses following the exact same `(listing value IS NULL OR criteria value IS NULL OR <compatible>)` null-passthrough pattern already used for price/beds — a listing whose pets/laundry couldn't be parsed (null) never disqualifies a match, and a user with no pets/laundry preference (null) is never filtered either. Pets: `cats_and_dogs`/`yes` on the listing satisfy any criteria value; otherwise the listing value must exactly equal the criteria value. Laundry: tiered — `in_unit` criteria only matches an `in_unit` listing; `on_site` criteria matches either `in_unit` or `on_site` listings (not `hookups`, which requires the tenant to supply their own washer/dryer and is treated as a weaker signal than a real laundry room). **AH-017:** commute filtering is *not* a SQL clause — it's a point-in-polygon check, which SQL can't express as cleanly as the other comparisons. `findMatchingUsers()`'s SQL now also selects `c.commute_isochrone`, and after the query returns, a JS post-processing step (`isPointWithinCommute()` from `lib/commute.ts`) filters out candidates whose listing coordinates fall outside their cached commute polygon before mapping rows down to `{user_id, max_daily_sms}`. Critically, this is a **local, synchronous check against an already-cached polygon** — the matching engine never calls the Mapbox Isochrone API itself (see `lib/commute.ts`'s header comment for the full "compute once, filter many times" rationale; the isochrone is computed once at criteria-set time in `app/api/auth/verify-otp/route.ts`). Null-passthrough applies here too: no commute filter set, or a listing with no coordinates, never disqualifies a match. **AH-019: enforces the per-user daily SMS cap** (`users.max_daily_sms`) before dispatch — `getTodaysSentCount()` counts today's `sent` rows for the user (America/Los_Angeles calendar day, see `lib/quietHours.ts`), and a match is skipped (not queued for later — a cap-skipped match just doesn't send that day) once the user is at/over their cap. `findMatchingUsers()`'s SQL also filters `NOT u.notifications_paused`. Emits `notification/send` for each match still under cap. **Fixed 2026-07-18 (issue #67) — chunked to stop real production 504 timeouts:** the `find-matches` work was originally one single unchunked Inngest step looping sequentially over every `listingId` in the triggering event, calling `findMatchingUsers()` (a DB round-trip) per listing plus `getTodaysSentCount()` per newly-seen candidate user — the exact same "unchunked sequential round-trips per item" failure class the pollers' own upsert step already hit once (issue #40/PR #41), just never applied here. A single `app/listings.upserted` event can carry hundreds of ids (RentCast's up-to-500-item runs collect every canonical id into one event), and this was confirmed in production: repeated real `propinno-matching-engine` HTTP 504s roughly every 6 hours (RentCast's own cron cadence) via `/api/admin/status`'s `recentFailures`, and `totalSent` stuck at 0 despite an active user and 895 real listings — strong evidence the function had never once completed against a real-volume batch. Fix: chunked the same way as the poller upsert (50 ids/chunk, `step.run('find-matches-chunk-N', ...)`), with the per-user daily-cap tally carried across chunk boundaries as a plain `Record<string, number>` returned from each chunk's step (not a shared in-memory `Map`, since a step's result must be independently serializable/memoizable for Inngest to replay it) — a user matching listings in two different chunks within the same run still gets capped correctly. All existing unit tests pass unchanged (every test's listingIds array fits in one 50-item chunk, so the observable behavior for small batches is byte-identical); two new tests cover the actual chunking (multiple `step.run` calls for >50 ids) and the cross-chunk cap-tally carry-over specifically.

**twilioSender.ts** — Triggered by `notification/send` event. **AH-019: respects quiet hours** — if the receiving user's current local time (hardcoded `America/Los_Angeles`, see `lib/quietHours.ts` for why) falls within `[quiet_start, quiet_end)`, the function calls `step.sleepUntil()` until `quiet_end` instead of sending immediately or dropping the notification; re-checks `notifications_paused` both before queuing the wait and again after waking (the wait can span up to ~24h, long enough for the user to pause in the meantime). Sends SMS via Twilio with listing details. Records in sent table. **AH-028: richer SMS body** — the outbound text is the real product moment (a subscriber acts on the text, not necessarily the dashboard), so the body now includes baths and a short pets/laundry summary alongside the original address/price/beds/link, not just the latter four. Extracted into a pure, exported `buildListingSmsBody()` so `tests/unit/twilioSender.test.ts` can assert on every present/absent-field combination directly. Same null-passthrough convention as everywhere else in this codebase (AH-018's matching-engine filters, `lib/format.ts`): a field a poller couldn't parse is omitted from the message entirely, never rendered as "unknown" — this keeps most Facebook/Realtor.com/Apartments.com/Apartment List/SpareRoom/Zumper messages unchanged today, since AH-018's pets/laundry parsing is still Craigslist/RentCast-only (RentCast is always null; see §7). When present, baths/pets/laundry render as one compact extra line (e.g. `1 ba · Cats+dogs OK · in-unit laundry`) between the existing address/price/beds line and the link — deliberately not one line per field, per the ticket's "stay scannable" instruction. Pets/laundry labels (`PETS_SMS_LABELS`/`LAUNDRY_SMS_LABELS` in the module) are SMS-terse (`Cats+dogs OK`, `in-unit laundry`) rather than full sentences, and are a separate, smaller vocabulary from whatever AH-027 (listing-card pet/laundry display, unstarted as of this ticket) eventually chooses for its own UI. **Real cost/length finding, not assumed:** the existing `·` separator already forces Twilio to encode these messages as UCS-2 (GSM-7 has no middle-dot code point), which caps segments at 70 chars (single) / 67 chars per segment when concatenated, rather than GSM-7's 160/153 — a pre-existing constraint, not introduced by this ticket. Checked against 8 real production `listings` rows with real baths data (disposable `tsx` script run against the live Supabase DB via the real `buildListingSmsBody()`, deleted before commit): every row was **already 2-3 SMS segments before this change**, purely from address+price+beds+URL length (e.g. a real craigslist row: 116 chars/2 segments; a real realtor.com row: 142 chars/3 segments) — the listing URL, not this ticket's addition, is most of a message's length. The new baths/pets/laundry line added 5-33 chars depending on how many of the three fields were present (baths-only: `\n1 ba` = 5 chars; baths+pets+laundry: `\n1 ba · Cats OK · in-unit laundry` = 33 chars). Of the 8 real rows checked, 4 stayed at the same segment count and 4 tipped from N to N+1 segments (e.g. one real craigslist row: 116→149 chars, 2→3 segments) — a real, non-trivial cost increase worth the reviewer seeing explicitly, not hidden behind an average. No truncation/length-capping logic was added — the ticket asked only to surface this tradeoff for review, not to build a segment budget; `lib/twilio.ts` has no existing length-awareness of any kind to build on (confirmed by reading it before starting).

**Fixed 2026-07-18 (launch-readiness audit, no ticket filed):** the `·` separator flagged above as a pre-existing constraint is now actually fixed — `buildListingSmsBody()` uses a plain hyphen (`-`) throughout instead. Found while auditing whether Propinno's paid APIs could handle an initial batch of signups: the A2P 10DLC campaign is registered as a **Sole Proprietor brand** (confirmed live via the Twilio Messaging Compliance API), which Twilio's own docs cap at 1,000 SMS segments/day to T-Mobile (~3,000/day across all US carriers) — a hard regulatory ceiling, unrelated to account balance. Since the middle dot forced every message into UCS-2 encoding (70 chars/segment vs. GSM-7's 160), it was roughly doubling real segment cost for a purely cosmetic choice, meaningfully eating into that ceiling. Also added a **daily SMS-send circuit breaker**: `step.run('check-sms-daily-budget', () => claimDailyBudget('twilio-sms', 300))` immediately before the actual Twilio call (placed after the quiet-hours wait, not before, so "today" reflects the real send day rather than the day the match was found) — unlike the poller budgets (RentCast, Mapbox amenities), SMS sends previously had no cap at all beyond the existing per-user `max_daily_sms`, so a burst of new signups with broad-matching criteria could have spent real Twilio balance (~$17 at the time of this audit, no code-side circuit breaker) with nothing to stop it. 300/day is a conservative starting cap: comfortably under the 1,000-segment T-Mobile ceiling (leaving headroom for Verify OTP sends), and cheap even at a low balance. A skipped send is neither recorded to `sent` nor treated as an error — it's naturally retried the next time that listing (or an equivalent one) is re-matched on a future poll cycle, same "skip today, don't lose the work permanently" philosophy as the poller budgets. **Two related items surfaced by this same audit that are explicitly *not* fixed here, since they need Pranav's direct action, not a code change:** (1) whether Twilio auto-recharge is enabled — payment-method-gated, checkable only via the Twilio console, not the API; if the balance hits $0 without it, Twilio fully suspends the account (documented error 30002), blocking OTP verification for every new signup, not just degrading gracefully; (2) upgrading the A2P brand from Sole Proprietor to Standard or Low-Volume Standard, which requires an EIN and a real business-registration process taking days to weeks per Twilio's own transition guide — the 300/day circuit breaker here is a stopgap, not a substitute for that upgrade if real signup volume approaches the 1,000/day T-Mobile ceiling.

**failureAlert.ts** — Triggered by `inngest/function.failed` event. Sends admin SMS alert via Twilio when any background job fails. Stores recent failures in Upstash Redis.

## 5. API routes (app/api/)

**POST /api/auth/send-otp** — Sends phone OTP via Twilio Verify. Rate limited.

**POST /api/auth/verify-otp** — Verifies OTP, creates user if new, sets auth cookie.

**POST /api/billing/create-checkout** — Creates Stripe Checkout Session for selected plan. Redirects to Stripe.

**POST /api/webhooks/stripe** — Stripe webhook (checkout.session.completed). Activates user, sets plan + expiry, saves criteria.

**GET /api/health** — Basic health check.

**POST /api/inngest** — Inngest serve handler. Registers all background functions.

**GET /api/admin/test-pipeline?secret=ADMIN_SECRET** — End-to-end smoke test. Inserts test listing → creates temp user with matching criteria → runs matching engine → sends SMS to ADMIN_PHONE → cleans up. Returns {success, listingId, matchedUserId, smsSid}.

**GET /api/admin/status?secret=ADMIN_SECRET** — Returns system health: DB connectivity, user/listing counts, recent Inngest failures from Redis.

**GET /api/listings/map** — Full-detail listing feed for the dashboard map. Session cookie auth + requires `status='active'` (paid, not just verified) — unlike `/api/listings/preview`, returns exact address/lat/lng/url. Query params `minPrice`/`maxPrice`/`minBeds`/`source` filter canonical listings with non-null lat/lng, capped at 500 results. Also returns `images` (listing image URLs, see §3/§7) as of the listing-images change, and `petsAllowed`/`laundryType` (AH-027) as of the pets/laundry-display change.

**GET /api/inbox** — In-app inbox feed (AH-016). Same active-user auth gate (via `lib/session.ts`'s `getActiveSessionUser()`). `sent` inner-joined to `listings` for the current user, `dismissed_at IS NULL`, ordered by `sent_at` desc, capped at 100. Returns `{items, unreadCount}`; each item includes `images` and, as of AH-027, `petsAllowed`/`laundryType`.

**GET /api/inbox/unread-count** — Lightweight count-only companion to the above (AH-016), used by the persistent nav badge so it doesn't have to pull the full listings join on every dashboard load. Returns `{count}` — rows where both `read_at` and `dismissed_at` are null.

**PATCH /api/inbox/[listingId]** — Mark an inbox item read or dismissed (AH-016). Body `{action: 'read' | 'dismiss'}`. Scoped to `(session userId, listingId)`; dismissing also stamps `read_at` so a dismissed item can never re-appear as unread. 404 if no matching `sent` row exists for this user.

**AH-019 — `app/dashboard/settings/actions.ts`** (server actions, not a route handler — same pattern as `app/checkout/actions.ts`): `getNotificationSettings()` and `updateNotificationSettings(input)`. Session-cookie auth + `limitRequest()` rate limiting, same as `checkout/actions.ts`. `updateNotificationSettings` validates with zod (`HH:MM` time strings padded to `HH:MM:SS`, `maxDailySms` clamped 1-100) before writing to `users`.

**GET /api/dashboard/commute** (AH-017) — Feeds the dashboard map's isochrone overlay. Same active-session auth gate as `/api/listings/map`/`/api/inbox` (`lib/session.ts`'s `getActiveSessionUser()`). Returns the current user's already-**cached** commute isochrone (`commuteAddress`, `commuteMode`, `commuteMaxMinutes`, and `{polygon, approximate}` or `null`) — never recomputes it, never calls Mapbox. Rate-limited like the other listing/inbox routes.

**POST /api/onboarding/parse-criteria** (AH-020) — Public (pre-auth) route, called from the onboarding page's "Describe what you're looking for" text input before a user/session exists — same trust tier and rate-limit pattern as `/api/auth/send-otp`. Body `{description: string}` (3-1000 chars). Delegates to `lib/nlpCriteria.ts`'s `parseCriteriaFromText()`, which calls the OpenAI API with forced tool-use to extract structured criteria, then re-validates the result with zod before returning it. Never writes to the DB itself — just returns `{criteria}` for the client to pre-fill the existing form fields, which the user still reviews/edits and submits through the unchanged `/api/auth/verify-otp` flow. Three failure modes, each a distinct HTTP status the UI can branch on: `503` (`reason: "not_configured"`, `OPENAI_API_KEY` unset), `422` (`reason: "invalid_response"`, the model's output didn't parse/validate), `502` (`reason: "api_error"`, network/API failure) — all return a user-safe `{error, reason}` body, never a crash.

**GET /api/favourites** (AH-022) — Saved/bookmarked listings feed: `favourites` inner-joined to `listings` for the current user, ordered by `saved_at` desc, capped at 100. Same active-user auth gate as `/api/inbox` (`lib/session.ts`'s `getActiveSessionUser()`). Backs both the `/dashboard/favourites` page and — via `components/use-favourites.ts` — the heart-icon "is this listing saved" state on the dashboard map and inbox, rather than a second, separate ids-only endpoint. Each item includes `images` and, as of AH-027, `petsAllowed`/`laundryType`.

**POST /api/favourites/[listingId]** (AH-022) — Saves a listing. `insert().onConflictDoNothing()` against the `favourites_user_id_listing_id_unique` constraint makes re-saving an already-saved listing idempotent at the DB level. Checks the listing exists first (404 if not) so a bad/stale id surfaces as a clean client error instead of a raw FK-violation 500.

**DELETE /api/favourites/[listingId]** (AH-022) — Unsaves a listing. Scoped to `(session userId, listingId)`, same pattern as `PATCH /api/inbox/[listingId]`; 404s if no matching row exists.

**GET /api/listings/[listingId]/amenities** (AH-023) — Nearby grocery/gym/transit/bike-share for a listing's detail card. Same active-session auth gate as `/api/listings/map`/`/api/inbox`/`/api/dashboard/commute` (`lib/session.ts`'s `getActiveSessionUser()`). Serves the already-cached `listings.amenities` column when present (`{...cache, cached: true}`, no Mapbox call); on a genuine cache miss, checks a daily cost-safety budget (`claimDailyBudget('amenities-lookup', 200)`, see §7/§8), then calls `lib/amenities.ts`'s `computeNearbyAmenities()` and persists the result before returning it (`cached: false`). Three non-error `reason` values the client can branch on, none of which get cached (so they're retried on the next view rather than permanently blanking a listing): `no_coordinates` (listing has no lat/lng to search from), `budget_exceeded` (daily lookup cap hit), `computation_failed` (Mapbox itself failed). 404 if the listing doesn't exist, 400 for a non-UUID id.

**GET/PATCH /api/criteria** (AH-026, issue #59) — Competitive parity with AH3000's "Search Profile" section: lets a subscriber view and edit their saved criteria any time after signup, not just once at onboarding. Same active-session auth gate as every other authenticated listing/inbox/favourites route (`lib/session.ts`'s `getActiveSessionUser()`) — mirrors, doesn't invent, the established pattern. `GET` returns the current user's full `criteria` row (price/beds/baths ranges, zips/neighborhoods, pets, laundry, commute fields); defaults to an all-null shape if no row exists (shouldn't happen — `verify-otp` always inserts one). `PATCH` is deliberately **not** the same "omit undefined = don't set" convention `verify-otp`'s onboarding schema uses — every field is `.nullable().optional()` in the zod schema so a present `null` explicitly clears a previously-set preference (e.g. removing a pets requirement), while a field absent from the body entirely is left untouched; only keys actually present in the body reach the SQL `SET` clause (Postgres rejects an empty `SET`, same guard `verify-otp` already has). Writes via `insert(criteria).values({userId, ...updates}).onConflictDoUpdate(...)`, the same upsert shape `verify-otp` uses, as a defensive fallback rather than assuming the row exists. **Commute isochrone recompute is conditional, not automatic:** `commuteAddress`/`commuteMode`/`commuteMaxMinutes` are compared against the row's current values (fetched first) — `computeCommuteIsochrone()` (AH-017, same function `verify-otp` calls) is only invoked when at least one of the three actually changed in this request, never on an unrelated edit like `priceMax`, so a subscriber tweaking their budget doesn't burn a Mapbox Isochrone API call. If the three post-edit values are no longer all present (e.g. the work address was cleared), the cached isochrone is set directly to `null` — disabling the commute filter — without calling Mapbox at all. Response includes `commuteRecomputed: boolean` so the client can tell the user their commute zone was recalculated. See §7's `lib/commute.ts` note (updated) and the dated AH-026 session note near the end of this file for full verification detail.

**lib/db/index.ts** — Drizzle postgres client. Uses Proxy pattern for build-time safety when DATABASE_URL absent. `prepare: false` for Supabase transaction pooler compatibility. **Fixed 2026-07-22 (issue #71):** every `postgres()` client construction (both the real-`DATABASE_URL` branch and the dummy-client/Proxy fallback) now also passes `max: 1, idle_timeout: 20`, previously uncapped (defaulting to up to 10 connections per client). Each serverless/Inngest invocation gets its own fresh module scope and therefore its own client — with no cap, a handful of concurrent invocations (a matching-engine run overlapping with pollers/twilioSender) could exhaust Supabase's transaction-mode pooler (PgBouncer, port 6543)'s shared connection-slot budget, causing intermittent query failures unrelated to the query's own correctness. `max: 1` costs nothing since one serverless invocation only ever runs one query at a time; `idle_timeout: 20` releases that connection back to the pooler quickly. See the dated session note near the end of this file for the full incident.

**lib/commute.ts** (AH-017) — Commute-time filtering: isochrone computation/caching + the point-in-polygon check, both documented in depth in the module's own header comment (read it before touching this file). Key exports:
- `computeCommuteIsochrone({address, mode, maxMinutes})` — geocodes the work address (reuses `lib/listings.ts`'s `geocode()`, the same helper the pollers use) and calls the Mapbox Isochrone API **once**, returning a `CommuteIsochroneCache` (polygon + metadata) to be cached on `criteria.commute_isochrone`. Called from `app/api/auth/verify-otp/route.ts` at onboarding-submit time, not per-match — see the "compute once" design note below. Never throws; returns null on any failure (missing token, geocode failure, non-ok API response, malformed response) so a Mapbox outage never blocks onboarding, it just leaves the commute filter inactive until recomputed.
- `pointInPolygon(point, geometry)` — hand-rolled ray-casting (even-odd rule) point-in-polygon test against a GeoJSON `Polygon`/`MultiPolygon`, handling holes and multiple disjoint polygons. No geometry library dependency was added for this (e.g. `@turf/boolean-point-in-polygon`) — the algorithm is a well-established handful of lines and is directly unit-tested (`tests/unit/commute.test.ts`), which felt more proportionate than a new dependency for one check.
- `isPointWithinCommute(lat, lng, isochrone)` — the matching engine's actual per-listing check: a fast local point-in-polygon test against an already-cached isochrone. Null-passthrough like the AH-018 pets/laundry filters: no commute filter set, or a listing with no coordinates, never disqualifies a match.

**lib/amenities.ts** (AH-023) — Nearby-amenity lookup (grocery/gym/transit/bike-share) for a listing's detail card, mirroring `lib/commute.ts`'s "pure computation, caller owns the cache" split. Key export: `computeNearbyAmenities(lat, lng)` — no DB access, no budget check (that's `app/api/listings/[listingId]/amenities/route.ts`'s job). Data source: **Mapbox Tilequery + Directions APIs, not Google Places** (no Google Places key exists anywhere in this project's env footprint, and this project already uses Mapbox exclusively — see the module's own header comment for the full investigation). Two Tilequery layers are queried separately against the `mapbox.mapbox-streets-v8` tileset, radius 805m (0.5mi per the ticket spec): `poi_label` (maki `grocery`/`supermarket` → grocery, `fitness-centre` → gym) and the dedicated `transit_stop_label` layer (maki `bus`/`rail`/`rail-metro`/`rail-light`/`ferry` → transit, `bicycle-share` → bike_share; `entrance` stop-type points filtered out in favor of named stop/station points). Querying transit via its own dedicated layer rather than `poi_label` matters in practice — confirmed live near 16th St Mission BART that `poi_label`'s single proximity-ordered 50-result cap gets dominated by restaurants/shops in a dense block, crowding out a transit stop that's genuinely closer than many of them. For each of the four categories, the nearest 1 candidate (by straight-line Tilequery distance, deduped by name) gets a real Mapbox Directions API walking-profile route computed — this is **real routing distance/time, not a straight-line estimate** (unlike AH-017's transit-isochrone approximation, which only exists because the Isochrone API has no transit profile at all; the Directions API does have a real `walking` profile, so there was nothing to approximate around here). The one genuinely approximated figure is `blocksApprox` (`SF_BLOCK_METERS = 80`, a documented rough citywide estimate, not derived from real block-boundary data) — converts the real walking distance into a human-readable "~N blocks" figure, flagged as approximate everywhere it's shown, same honesty standard AH-017 applied to its transit multiplier. Never throws: returns `null` only if both Tilequery layers fail outright or `MAPBOX_TOKEN` is unset; returns a real (cacheable) `{amenities: [], computedAt}` when Mapbox answers successfully but finds nothing within range; a single candidate's failed Directions call just drops that one candidate rather than failing the whole lookup.

**Design — compute once, cache forever, one nearest amenity per category:** same principle as AH-017's isochrone caching — a listing's coordinates don't change, so recomputing its nearby-amenity list on every pageview would be pure waste. `app/api/listings/[listingId]/amenities/route.ts` checks `listings.amenities` first and only calls `computeNearbyAmenities()` on a genuine cache miss, then persists the result. Unlike AH-017 (computed eagerly at criteria-set time, one call site), this is computed **lazily**, the first time a listing's detail card is actually opened — justified because most ingested listings are never clicked, so eager per-listing computation at poll time would burn Mapbox calls on data nobody looks at; lazy-on-first-view only pays for listings someone actually cares about. Bounded to one nearest candidate per category (not an exhaustive list) to cap worst-case cost at 2 Tilequery + 4 Directions calls per newly-computed listing and keep the detail card focused — matches the ticket's own two examples (one instance each of "8 min to BART" / "2 blocks to Safeway"), not a scrollable list of every nearby option.

**Cost safety — a per-day cap on new (cache-miss) lookups, not a per-poller-run budget:** `lib/pollerBudget.ts`'s `claimDailyBudget('amenities-lookup', 200)` bounds how many *previously-uncomputed* listings get a live Mapbox lookup per day — cache hits (the common case once a listing's been viewed once) never touch this cap or Mapbox at all. 200/day × up to 6 Mapbox calls each (2 Tilequery + up to 4 Directions) is a worst-case ~36k calls/month, comfortably under both APIs' 100k/month free tier (Tilequery: 100k free then $1.50/1k; Directions: 100k free then $2.00/1k — checked against Mapbox's own pricing page, 2026-07) even at sustained daily volume. Real cost should be far under that ceiling in practice, same as this project's other budget caps.

**Design — compute once, filter locally, never call the Isochrone API in the matching engine's hot path:** the ticket's own guidance was explicit that calling Mapbox's Isochrone API once per listing×user check inside `matchingEngine.ts` would be slow, cost real money at volume, and risk hitting Mapbox's rate limit (300 req/min) once there's real traffic. Instead, the isochrone is computed exactly once per user, whenever their commute criteria is set/changed — originally onboarding submit only; as of **AH-026** (2026-07-17), `PATCH /api/criteria` (the post-signup "Search Profile" edit page) also calls `computeCommuteIsochrone()` the same way, but only when `commuteAddress`/`commuteMode`/`commuteMaxMinutes` actually changed in that request (see §5's `/api/criteria` entry) — and the matching engine's check (`isPointWithinCommute()`) is purely local against that cache — see `inngest/functions/matchingEngine.ts`'s `findMatchingUsers()` in §4.

**Known limitation — no real transit routing (documented, not silently approximated):** Mapbox's Isochrone API supports exactly four profiles — `driving-traffic`, `driving`, `walking`, `cycling` — confirmed against Mapbox's own API docs (2026-07). There is no transit/public-transit profile on this API or on any other Mapbox product; Mapbox does not offer public-transit routing at all, and Propinno has no other transit-capable routing API in its dependency/env footprint (see §8). `commute_mode='drive'` and `'bike'` map onto Mapbox's real `driving`/`cycling` profiles. `commute_mode='transit'` is an **explicitly-labeled approximation**: computed via the `walking` profile with the user's requested max-minutes multiplied by `TRANSIT_TIME_MULTIPLIER` (2.5, a documented-but-not-schedule-derived estimate — see the in-code rationale) before being sent to the Isochrone API, capped at Mapbox's 60-minute contour maximum. This produces an isotropic (roughly circular) polygon, which is a materially wrong shape for real transit reach (corridor-shaped, elongated along rail/bus lines) — it will overestimate reach perpendicular to transit corridors and underestimate reach along fast lines like BART. The `approximate: true` flag on the cached result surfaces this everywhere it's user-visible: the onboarding form shows an explicit disclaimer under the transit mode selector, and the dashboard map's "Commute zone" badge appends "(estimated, not real transit routing)" when the mode is transit. Verified live against Mapbox's real API during this ticket's browser verification (see the AH-017 checkpoint) — a real "1 Ferry Building, San Francisco, CA" address with `mode='transit'`, `maxMinutes=30` correctly geocoded, computed via the `walking` profile at `effectiveMinutes=60` (30×2.5, capped), and returned a real polygon that was then confirmed to correctly include/exclude test points via the production `isPointWithinCommute()` function against the live cached data.

**lib/nlpCriteria.ts** (AH-020, migrated to OpenAI 2026-07-18) — `parseCriteriaFromText(description)`: calls the OpenAI API (`gpt-4o-mini`, `openai` SDK's Chat Completions endpoint) with a single tool (`extract_apartment_criteria`) and a forced `tool_choice`, so the model returns a structured object rather than prose to regex/parse. OpenAI returns the tool call's arguments as a raw JSON string (unlike Anthropic's already-parsed `tool_use.input`) — parsed via `JSON.parse()` inside its own try/catch, a real (if rare) extra failure mode the Anthropic version didn't need. The parsed object is then re-validated with zod (`parsedCriteriaSchema`) before ever being trusted — type/enum checks matching `lib/db/schema.ts`'s real `criteria` value domains (`pets`/`laundry`/`commuteMode` enums identical to `app/api/auth/verify-otp/route.ts`'s own zod schema), plus sanity range bounds (price/beds non-negative and capped, `priceMin<=priceMax`, `bedsMin<=bedsMax`, commuteMaxMinutes 1-180) and zip-shape/length checks — not a hard SF-neighborhood whitelist, since the `neighborhoods` DB column is free text and a fixed list would reject legitimate neighborhoods; the model is steered toward real SF names via the tool description/system prompt instead. Returns a discriminated `{success:true, data} | {success:false, reason, message}` — never throws. Three failure reasons: `not_configured` (`OPENAI_API_KEY` unset — checked the same way `NEXT_PUBLIC_MAPBOX_TOKEN`'s absence is surfaced in `dashboard-map.tsx`, adapted since this key must stay server-only), `invalid_response` (no tool call returned, malformed tool-call-argument JSON, or zod validation failed), `api_error` (network/SDK error, reported to Sentry). Does **not** geocode the commute address or compute an isochrone itself — deliberately, to avoid duplicating `lib/commute.ts`'s existing single call site and burning a Mapbox call on an address the user might still edit before submitting; the existing `computeCommuteIsochrone()` call in `verify-otp/route.ts` handles that, unchanged, once the reviewed form is actually submitted. Rewritten to call OpenAI instead of requesting a new Anthropic key, matching the key that was actually deployed — see the 2026-07-18 session note below for the full incident and migration writeup.

## 9. Connection notes

**DATABASE_URL must use the transaction pooler** (`aws-1-us-west-1.pooler.supabase.com:6543`) with `?sslmode=require`. The direct host (`db.*.supabase.co`) is IPv6-only; Vercel serverless is IPv4-only. The pooler hostname generation matters: this project uses `aws-1`, not `aws-0`.

**Inngest** must be connected to the Vercel deployment for cron jobs to fire. Check at app.inngest.com.

**Twilio A2P 10DLC** — Campaign `CMbd88fe6faade4e8e04ab159e85081043` status **Verified** (confirmed live in Twilio console 2026-07-17), Sole Proprietor use case, connected brand `BNd9973f46ff7585031bf66e477ac090f6`. Real US carrier SMS delivery is NOT blocked. Current throughput cap under the Sole Proprietor package is ~3,000 segments/day — fine at current scale, but would need an upgrade to the Standard package (requires more business verification) if subscriber volume grows enough to approach that ceiling.

**Stripe: this account has TWO separate test environments, only one of which has real data.** Stripe migrated "Test mode" into its newer "Sandboxes" feature; this account now has a classic **"Test mode"** environment (same account ID as everything else, `acct_1TnD6NPNHERgVBVt` — this is where the real `STRIPE_PRICE_30DAY`/`STRIPE_PRICE_90DAY` products/prices actually live) AND a separate, auto-created **"Propinno sandbox"** (different account ID, `acct_1TnD6UPAyKZQ52yq`, completely empty). Confirmed 2026-07-17: production checkout broke for exactly this reason — a key copied from the Stripe dashboard's default/highlighted API keys view was the empty sandbox's key, not classic Test mode's, producing a `resource_missing`/"No such price" error even though the key itself was perfectly valid. **If `STRIPE_SECRET_KEY` ever needs to be rotated again: copy it from `.env.local` locally (already proven correct) rather than re-fetching from the Stripe dashboard**, or if fetching fresh, explicitly select the "Test mode" environment (not "Propinno sandbox") in Stripe's account/sandbox switcher first — the dashboard's default view and the classic Test mode's own price-lookup UI pages can both misleadingly show 0 products even when the account genuinely has active ones (a sandboxes-migration UI quirk, not a real data-loss signal — the API layer remains authoritative).

**Stripe webhooks hit the same dashboard-vs-API split, one layer deeper.** After fixing the key, checkout sessions completed and were paid (`status=complete`), but `/api/webhooks/stripe` never received anything — confirmed via `stripe.webhookEndpoints.list()` (same `.env.local` key that creates real sessions) returning **zero** endpoints, even after a webhook destination was created and showed "Active" through the Stripe *dashboard* UI. The dashboard browser session and the API key are apparently pinned to different backend contexts regardless of what account ID the URL bar shows — the fourth instance of this exact class of bug in one debugging session (also hit on the Product catalog page and the Payments/Transactions page, both of which showed empty/onboarding states for data that provably existed via direct API calls). **Fix: create webhook endpoints via `stripe.webhookEndpoints.create()` (API), never via the dashboard UI, for this account** — verify with `stripe.webhookEndpoints.list()` using the same key immediately after to confirm it's actually visible in the right context before trusting it.

**Vercel marks some env vars `Sensitive`, which silently blocks reading them back — including via `vercel env pull`.** `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and `MAPBOX_TOKEN` are all marked this way in this project; pulling them returns the literal string `[SENSITIVE]`, not the real value, with no error. This made a manual copy-paste mismatch (stale/wrong webhook secret in Production) look identical to "everything should be correct" from every angle available at the time — there was no way to confirm-by-reading. The reliable fix once this class of problem is suspected: `vercel env rm <NAME> production` then pipe the known-correct value directly from `.env.local` into `vercel env add <NAME> production` — this sets the value with byte-for-byte precision and removes copy-paste as a variable, even though the result still can't be read back afterward to double check.

**Vercel CLI is now set up for this project** (2026-07-17, via `npx vercel` — auth picked up Pranav's existing browser session with zero manual login steps, then `vercel link` to `nullcoders-projects/propinno`). Prefer `vercel env add/rm` piped from a known-good local value over asking Pranav to copy-paste through the dashboard UI for any future secret rotation — this session needed four full round-trips (Stripe key, webhook secret via dashboard, webhook secret via API, Mapbox token) before landing on this as the reliable pattern.

## 2026-07-16 — Fix: poller upsert step timing out (issue #40, PR #41)
Context: Every RentCast poller run on 2026-07-16 failed with `FUNCTION_INVOCATION_TIMEOUT` (Vercel's 60s ceiling on `app/api/inngest/route.ts`, added the same week for the Craigslist/Apify call). Zero new listings ingested from any source that day — Craigslist was separately blocked on a missing `APIFY_API_TOKEN` at the same time.
Root cause: `dedupeAndUpsertListings()` (`lib/listings.ts`) processes its input sequentially, 2 blocking DB round-trips per item (dedupe `SELECT` + `INSERT ... ON CONFLICT`), all inside one un-chunked `step.run()` call. RentCast requests up to 500 listings/run; at 500 × 2 sequential round-trips with real Vercel(iad1)↔Supabase(us-west-1) latency, this reliably exceeded 60s. Craigslist's 80-item cap kept it under the same ceiling — latent, not yet triggered.
Fix: Both pollers now chunk the upsert into multiple `step.run('upsert-listings-chunk-N', ...)` calls (50 items/chunk), accumulating results before the `trigger-matching` event dispatch. Each `step.run()` is a separately checkpointed Inngest invocation with its own fresh `maxDuration` budget, so this fixes the timeout without changing `dedupeAndUpsertListings()` itself or fighting Inngest's execution model.
Consequences: `tests/unit/rentcastPoller.test.ts` and `tests/unit/craigslistPoller.test.ts` now mock chunked step names (`upsert-listings-chunk-0`, etc.) instead of a single `upsert-listings` step — any future poller changes touching the upsert step need to match this pattern. `dedupeAndUpsertListings()`'s underlying per-item sequential-round-trip cost is still there per chunk; if a poller's per-run item count or the chunk size grows significantly, the same failure mode could resurface — a batched (single multi-row `SELECT`/`INSERT`) rewrite of `dedupeAndUpsertListings()` itself would be the more durable fix if that happens.

## 2026-07-16 — AH-019: Notification settings (quiet hours, daily cap, pause/resume)
Context: AH3000 fast-follow ticket — user-configurable notification preferences. Worked in parallel with AH-016 (in-app inbox) in a separate worktree; no file overlap.
Schema: `users` gained `quiet_start`/`quiet_end` (time, default `21:00:00`/`08:00:00`), `max_daily_sms` (int, default `20`), `notifications_paused` (bool, default `false`). Migration `drizzle/0001_ah-019-notification-settings.sql`, applied directly to the `klyzbaepzyyhykyeobbp` Supabase project via MCP `apply_migration` (confirmed landed in `public.users`, not `auth.users`, which also has a same-named `users` table in this project — schema-qualify any ad hoc query against this DB from now on to avoid ambiguity). Defaults were chosen deliberately, not left at framework defaults: 21:00-08:00 quiet hours changes behavior for all existing users (no one is texted overnight going forward) but errs toward what users almost certainly want from an "apartment alert" product; `max_daily_sms=20` is generous enough not to silently throttle a real subscriber (RentCast alone can produce many matches per run) while still bounding worst-case Twilio spend per user per day; `notifications_paused` defaults `false` so existing active subscribers keep receiving texts exactly as before until they opt to pause.
Decision — quiet hours enforcement uses `step.sleepUntil()`, not a queue table or cron sweep: `inngest/functions/twilioSender.ts` checks `lib/quietHours.ts`'s `isWithinQuietHours()` against the receiving user's `quiet_start`/`quiet_end` at send time; if within the window, computes the next `quiet_end` instant via `nextQuietHoursEnd()` and calls `step.sleepUntil('wait-for-quiet-hours-end', ...)`. This durably suspends that one Inngest function invocation (Inngest persists step state, so it survives deploys/restarts) rather than requiring a separate poller to periodically re-check a "pending notifications" table — matches the pattern the ticket's implementation notes explicitly asked for.
Decision — hardcoded `America/Los_Angeles`, not UTC, and not a fixed offset: Propinno has no stored per-user timezone field and is an SF-only product, so every user's quiet hours are meant to be interpreted in Pacific time regardless of where the request happens to be served from. A fixed UTC offset (e.g. always -7 or -8) would be wrong for half the year across the March/November DST transitions; `lib/quietHours.ts` instead resolves the real IANA-zone offset at the specific instant in question via `Intl.DateTimeFormat`, verified correct across both 2026 DST transition dates in `tests/unit/quietHours.test.ts`. This is called out explicitly (not silently assumed) per the ticket's instructions, and documented in the module's own header comment.
Decision — daily cap enforced in `matchingEngine.ts`, not `twilioSender.ts`: a cap-skipped match is dropped for the day, not queued for later (quiet hours and the cap are different concerns — quiet hours delay a send, the cap prevents one). `findMatchingUsers()`'s SQL filters `NOT u.notifications_paused` and returns `max_daily_sms`; a new `getTodaysSentCount()` counts today's `sent` rows for the user using the same Pacific-day boundary as quiet hours (`lib/quietHours.ts`'s `startOfLocalDay()`, exported for reuse). An in-run `Map` tracks tentative dispatches within a single matching-engine invocation so one run matching a user against several listings can't blow past the cap before any of that run's `sent` rows actually exist (they're written later, asynchronously, once each `twilioSender` invocation completes — including after a quiet-hours wait).
Decision — defensive pause re-check after the quiet-hours wait: since a delayed send can wait up to ~24h (worst case: quiet hours cover nearly the full day), `twilioSender.ts` re-checks `notifications_paused` immediately after waking, in addition to the pre-wait check — a user who pauses mid-wait shouldn't still get texted once the window ends. This is a small addition beyond the ticket's literal checklist, justified because "pause/resume" needs a real enforcement point somewhere for the feature to functionally exist, and the quiet-hours delay is exactly where a stale pre-wait snapshot would otherwise cause a wrong send.
UI: New `/dashboard/settings` route (Server Component auth gate, same `status='active'`-only pattern as `/dashboard`) wrapping client component `components/notification-settings-form.tsx` — pause/resume toggle, quiet-hours start/end (`<input type="time">`), daily text limit, save button via new server actions `app/dashboard/settings/actions.ts` (`getNotificationSettings`, `updateNotificationSettings`; session-cookie auth + rate-limited, same pattern as `checkout/actions.ts`). `components/dashboard-map.tsx` gained a gear-icon link to the new settings page next to the existing Filters button.
Tests: `tests/unit/quietHours.test.ts` (new) covers `isWithinQuietHours`/`nextQuietHoursEnd`/`startOfLocalDay` directly, including both 2026 DST transition dates. `tests/unit/twilioSender.test.ts` extended with fake-timer-based cases for immediate-send-outside-quiet-hours, paused-skips-without-sleeping, delayed-send-then-sends, and delayed-then-paused-during-wait-skips. `tests/unit/matchingEngine.test.ts` extended with cases for under-cap dispatch, at-cap skip, and the in-run multi-listing tally.
Verified in a real browser (not just the sandboxed preview): started a second dev server on port 3010 from this worktree specifically (the shared preview-pane server was bound to the main repo checkout, not this branch, and lacked the new route — confirmed via a 404 before switching), created a disposable test user through the real onboarding + dev-mode OTP (`000000`) flow, flipped `status` to `active` via Supabase `execute_sql`, confirmed the settings page loads with the correct schema defaults, saved changed values (quiet hours, cap, pause) and confirmed both the immediate UI state and a full page reload reflect the persisted DB row, then flipped status back to `pending_payment` and confirmed `/dashboard/settings` redirects to `/checkout` instead of rendering. Test user and its cascade-deleted `criteria`/`sent` rows were removed afterward.
Consequences: `NOT u.notifications_paused` and the per-row `getTodaysSentCount()` query add a small amount of per-match overhead to `matchingEngine.ts` (one extra `db.execute` call per distinct matched user per run, not per listing) — acceptable at current volume, worth revisiting if matched-user counts grow much larger. Row Level Security is disabled on all `public` tables in the `klyzbaepzyyhykyeobbp` Supabase project, `public.users` included (pre-existing, unrelated to this ticket — flagged here because it surfaced while inspecting the `users` table schema; not fixed as part of this PR).

## 2026-07-16 — AH-017: Commute-time filtering (Mapbox Isochrone)

Context: Filter listings by commute time to a workplace, per issue #29 and AH3000's "I understand your commute" teardown feature (`docs/AH3000_teardown.md` §7 — a 30-min transit isochrone). Sequenced after AH-018 per `CLAUDE.md`'s priority list.

Schema: `criteria` gained `commute_address` (text), `commute_max_minutes` (int), `commute_mode` (text), `commute_isochrone` (jsonb) — all nullable, migration `drizzle/0004_ah-017-commute-filtering.sql`, generated via `npx drizzle-kit generate` against `main`'s existing `0000`-`0003` history. Applied to the live Supabase project by running the generated SQL directly via a one-off `postgres`-client script (same fallback the AH-018 session used and documented — the Supabase MCP `apply_migration` tool hit `net::ERR_FAILED` again this session, and `drizzle-kit migrate` is confirmed not usable against this project since `drizzle.__drizzle_migrations` has zero rows despite four real migrations already being live).

Decision — plain columns + untyped jsonb, not a pgEnum or a typed Drizzle jsonb column: `commute_mode` follows the same "plain text, app-layer-checked string union" convention as `listings.source`/`pets`/`laundry` in this schema. `commute_isochrone` is deliberately left untyped at the schema level (`jsonb('commute_isochrone')`, no `.$type<...>()`) matching `listings.raw`'s existing convention — callers cast the shape explicitly via `lib/commute.ts`'s exported `CommuteIsochroneCache` type. This also sidesteps a real import-cycle risk: `lib/commute.ts` imports `geocode` (a value) from `lib/listings.ts`, which imports the `listings` table (a value) from `lib/db/schema.ts` — if `schema.ts` imported `CommuteIsochroneCache` as a value-level generic argument from `lib/commute.ts`, that would be a genuine runtime cycle; leaving the column untyped avoids the question entirely.

Decision — compute once at criteria-set time, cache, never call the Isochrone API from the matching engine: this was explicit, non-negotiable guidance from the ticket itself, not a judgment call — a live Isochrone API call per listing×user check in `matchingEngine.ts`'s hot path would be slow, cost real money at volume, and risk Mapbox's rate limit (300 req/min) once there's real traffic. `lib/commute.ts`'s `computeCommuteIsochrone()` is called exactly once, in `app/api/auth/verify-otp/route.ts`, only when all three of `commuteAddress`/`commuteMaxMinutes`/`commuteMode` are present together in the submitted criteria (they're one optional field group in the onboarding form). It geocodes the work address by reusing `lib/listings.ts`'s existing `geocode()` helper (the same one the pollers use — no new geocoding code), calls the Mapbox Isochrone API once, and returns a `CommuteIsochroneCache` object cached straight onto `criteria.commute_isochrone`. `matchingEngine.ts`'s `findMatchingUsers()` then does a **local, synchronous** point-in-polygon check (`isPointWithinCommute()`) against that cached polygon as a post-SQL-query JS filter step — never a live API call. There is no "edit criteria" UI anywhere in this codebase yet (pets/laundry criteria can't be edited post-onboarding either, as of AH-018) — criteria is only ever written once, at onboarding submit, so this is the one and only call site today; a future edit-criteria feature must call `computeCommuteIsochrone()` the same way to keep the cache from going stale, which is called out explicitly in `lib/commute.ts`'s header comment as a note for whoever builds that.

Decision — no real transit routing exists on Mapbox, at all: investigated before assuming anything (per the ticket's explicit instruction not to skip this). Confirmed against Mapbox's own Isochrone API documentation that it supports exactly four profiles — `driving-traffic`, `driving`, `walking`, `cycling` — and that Mapbox does not offer any public-transit routing product at all, on any API. Propinno has no other transit-capable routing API in its env/dependency footprint, and adding one as a dependency of this single ticket was judged out of scope. Resolution: `drive`→Mapbox `driving`, `bike`→Mapbox `cycling` (both real routing, no approximation). `transit`→Mapbox `walking`, with the user's requested max-minutes multiplied by a documented constant (`TRANSIT_TIME_MULTIPLIER = 2.5`, in `lib/commute.ts`) before being sent to the Isochrone API, capped at Mapbox's 60-minute contour ceiling. This constant is an engineering estimate (a real transit trip's door-to-door effective speed, including wait/transfer overhead, in a dense city like SF is meaningfully faster than walking but far short of rail line-haul speed) — **not** derived from any real Muni/BART schedule or GTFS data, and it produces an isotropic (circular-ish) polygon rather than the corridor-shaped reach real transit actually has. This is surfaced everywhere it's user-visible, not silently presented as real transit accuracy: an `approximate: true` flag on the cached result, an explicit disclaimer under the mode selector in the onboarding form ("Transit commute times are a rough estimate, not real transit routing..."), and a "(estimated, not real transit routing)" suffix on the dashboard map's commute-zone badge when the mode is transit.

Decision — hand-rolled point-in-polygon, no new geometry dependency: `lib/commute.ts`'s `pointInPolygon()` is a standard ray-casting (even-odd rule) implementation, handling polygon holes and MultiPolygon. No geometry library (e.g. `@turf/boolean-point-in-polygon`) exists in this project's dependencies today, and the algorithm itself is a well-established ~15 lines, directly unit-tested (12 cases in `tests/unit/commute.test.ts` covering simple polygons, holes, and MultiPolygons) — adding a new dependency for one function felt disproportionate given the project's existing "no geometry lib" baseline, though it's a reasonable enough thing to revisit if this project ever needs more geometry operations than this one check.

## 2026-07-18 — Critical production fix #1: matchingEngine.ts 504 timeouts (issue #67)

Context: while checking whether Propinno was actually ready to start marketing (not a scoped ticket), queried `/api/admin/status` in production and found `totalSent: 0` despite 1 active user and 895 real listings, plus `recentFailures` showing repeated real `propinno-matching-engine` HTTP 504s roughly every 6 hours — matching RentCast's `0 */6 * * *` cron cadence exactly.

Root cause: `matchingEngine.ts`'s `find-matches` step was a single unchunked Inngest step looping sequentially over every `listingId` in the triggering `app/listings.upserted` event, calling `findMatchingUsers()` (a DB round-trip) per listing plus `getTodaysSentCount()` per newly-seen candidate user. A single poller run can hand it hundreds of ids at once (RentCast's up-to-500-item runs collect every canonical id into one event) — the exact same "unchunked sequential round-trips per item" failure class already found and fixed once for the pollers' own upsert step (issue #40/PR #41, 2026-07-16), just never applied here. This function had, in all likelihood, never once completed successfully against a real-volume batch since the pipeline first went live.

Fix: chunked `listingIds` 50/chunk (same convention as the poller fix), with the per-user daily-cap tally carried across chunk boundaries as a plain serializable `Record<string, number>` returned from each chunk's `step.run()`, rather than a shared in-memory `Map` — a step's result must be independently memoizable for Inngest to replay it correctly on a retry, and a `Map` isn't. See §4's `matchingEngine.ts` entry for the exact mechanics.

Verification: `tsc --noEmit`/`npm run lint`/`npm run build` all clean; `npm test` 332 passing. All 7 pre-existing `matchingEngine.test.ts` tests pass **unchanged** — every test's `listingIds` array is small enough to fit in one 50-item chunk, so observable behavior for normal-size batches is byte-identical to before the fix. Two new tests cover the actual chunking (51 ids → 2 distinct `step.run` calls, 2 `findMany` calls) and the cross-chunk cap-tally carry-over (a user matching in both chunk 0 and chunk 1 within the same run still gets capped, without a duplicate `getTodaysSentCount` call). PR #68, merged.

## 2026-07-18 — Launch-readiness audit: SMS encoding fix + daily budget circuit breaker

Context: Pranav asked directly whether all paid APIs were "well funded enough to handle the initial batch of users." Rather than answering from memory, checked real account state across every paid dependency: Twilio (balance via the REST API, A2P campaign registration via the Messaging Compliance API), Apify/Mapbox/OpenAI (could not verify — no local API keys for the first and third, and only a public-scoped token for the second), Supabase (project health only, no plan-tier visibility via the MCP tool), RentCast (not a scaling risk — already self-capped independent of subscriber count via `lib/pollerBudget.ts`).

Two real, concrete, verified findings from that audit — both fixed here:

1. **A2P 10DLC campaign registered as a Sole Proprietor brand.** Confirmed live via `messaging.twilio.com/v1/Services/{sid}/Compliance/Usa2p` — `campaign_status: VERIFIED`, but Sole Proprietor is Twilio's lowest-trust registration tier. Twilio's own docs (`twilio.com/docs/trust-hub/registrations/a2p-10dlc-brand`) cap that tier at **1,000 SMS segments/day to T-Mobile** (~3,000/day across all US carriers) — a hard regulatory ceiling enforced by the carrier, independent of account balance. Once hit, T-Mobile subscribers specifically stop receiving anything (OTP or match alerts) until midnight Pacific, silently (error 30023).
2. **The outbound SMS separator (`·`, a middle dot) forces UCS-2 encoding.** The middle dot isn't in the GSM-7 default character set, so its presence anywhere in the message body forces the *entire* message into UCS-2 (70 chars/segment instead of 160/153) — this was already flagged as a known, unfixed cost finding in AH-028's own entry above ("a pre-existing constraint, not introduced by this ticket... No truncation/length-capping logic was added"), but nobody had connected it to the Sole Proprietor throughput ceiling until this audit. Doubling segment cost per message roughly halves how many subscribers can actually be notified before hitting the 1,000/day cap.

Fix 1: `buildListingSmsBody()` now uses a plain hyphen (`-`) instead of `·` throughout — a one-line-equivalent change that restores GSM-7 encoding (and therefore ~2x the real segment budget) for typical messages, with zero visual/informational loss.

Fix 2: added a **daily SMS-send circuit breaker** — `step.run('check-sms-daily-budget', () => claimDailyBudget('twilio-sms', 300))` in `twilioSender.ts`, checked immediately before the actual Twilio `messages.create()` call (after the quiet-hours wait, not before, so "today" reflects the real send day). Unlike the poller-side budgets (RentCast's 20/day, Mapbox amenities' 200/day), Twilio SMS sends had **no cap at all** beyond the existing per-user `max_daily_sms` — a burst of new signups with broad-matching criteria could spend real Twilio balance (~$17 at the time of this audit) with nothing to stop it. 300/day is a conservative starting point: well under the 1,000-segment T-Mobile ceiling (leaving headroom for Verify OTP sends), and cheap even at a low balance — same "safety net, not a business limit" philosophy documented in `rentcastPoller.ts`'s original budget comment. A skipped send isn't recorded to `sent` and isn't treated as an error — it's naturally retried whenever that listing (or an equivalent match) resurfaces on a future poll cycle.

**Explicitly not fixed here — these need Pranav's direct action, not a code change:**
- Whether Twilio auto-recharge is enabled. This is a payment-method setting, checkable only via the Twilio console (not exposed via the REST API in any way this session found). If the balance hits $0 without auto-recharge, Twilio fully suspends the account (documented error 30002) — this blocks OTP verification for every new signup, not just SMS notifications, so it's worth confirming before any real marketing push.
- Upgrading the A2P brand from Sole Proprietor to Standard or Low-Volume Standard. Per Twilio's own transition guide, this requires an EIN/Tax ID and a real business-registration process (verification can take "several days or even several weeks"). The 300/day circuit breaker added here is a stopgap that prevents a silent, ungraceful failure — it does not raise the actual regulatory ceiling. If real signup volume approaches it, this upgrade is the actual fix.

Verification: `tsc --noEmit`/`npm run lint`/`npm run build` all clean; `npm test` 334 passing (up from 333 — one new case in `tests/unit/twilioSender.test.ts` for the budget-exceeded skip path, plus every existing body-string assertion in that file updated from `·` to `-`). Real live checks (not just unit tests): confirmed the Sole Proprietor campaign status and the $17.07 balance directly via the Twilio REST API using this environment's real credentials, and confirmed the exact GSM-7/UCS-2 mechanism by inspecting the real message-body template rather than assuming it from general SMS knowledge.

## 2026-07-22 — Critical production fix #3: lib/db/index.ts connection pool exhaustion (issue #71)

Context: checking whether the core matching/notification loop was actually delivering real SMS end-to-end (still `totalSent: 0` in production days after the matching-engine chunking fix), `/api/admin/status` showed a new, different failure signature starting 2026-07-21: repeated `getTodaysSentCount()` query failures (`"Failed query: SELECT count(*)::int as count FROM sent WHERE user_id = $1 AND sent_at >= $2"`), distinct from the earlier HTTP 504 timeouts already fixed in issue #67.

Diagnosis: ran the exact failing query directly against Postgres (via the Supabase MCP, using the literal parameter values from the failure log) — it succeeded instantly, ruling out a schema/SQL/data problem. The failure was specific to the app's own DB connection path, not the query itself.

Root cause: `lib/db/index.ts` constructs a `postgres()` client (from the `postgres` npm package, via `drizzle-orm/postgres-js`) with no `max` connection cap — `{ prepare: false }` only. `DATABASE_URL` points at Supabase's transaction-mode pooler (PgBouncer, port 6543), which has a limited shared connection-slot budget. Every serverless/Inngest function invocation gets its own fresh module scope and therefore its own `postgres()` client; with no cap, each defaults to up to 10 connections. Craigslist listings alone grew from 516 to 2,555 rows in the 4 days between the two fixes, meaning far more matching-engine chunks and a higher chance of multiple Inngest functions (pollers, matchingEngine, twilioSender) running concurrently — enough aggregate concurrent connection demand across separate serverless instances to exhaust the pooler's slots, causing intermittent query failures with no other symptom. This is a well-known failure pattern for serverless apps sitting behind PgBouncer transaction-mode pooling.

Fix: both `postgres()` client constructions in `lib/db/index.ts` (the real-`DATABASE_URL` branch and the dummy-client/Proxy fallback) now pass `{ prepare: false, max: 1, idle_timeout: 20 }` via a shared `POOL_OPTIONS` constant. `max: 1` is correct for serverless — one invocation only ever runs one query at a time (queries within an invocation are sequential), so capping at 1 costs nothing while letting far more concurrent invocations succeed within the pooler's real capacity. `idle_timeout: 20` releases that single connection back to the pooler quickly rather than holding it for a container's full (possibly long) lifetime.

Verification: `tsc --noEmit`/`npm run lint`/`npm run build` all clean; full unit suite passing. No new unit test was added specifically for this change — it's a connection-pool-configuration change to a well-tested external library with no meaningful way to unit-test the actual pooling behavior in isolation, and this file has no existing test coverage of its own to extend. Real-world verification (confirming the fix actually holds under production load, not just that the code compiles) to be done directly against the deployed fix once merged.
